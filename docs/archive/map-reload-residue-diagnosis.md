## 用户确认的复现顺序

1. Typhoea 的删面 Mesh、材质/贴图替换生效。
2. 全部注释该 Mod INI，按 F10，当场恢复原 Mesh。
3. 切换地图后，修改过的网格和贴图**都回来**；INI 仍为注释状态，再按 F10 也不能撤销。
4. 取消注释并 F10，Mesh 消失；再次注释/F10 不能恢复。

这是两个需要分别取证的问题：第 3 步旧引用来源，与第 4 步赋值失败后的恢复遗漏。
不允许把“缓存仍有对象”直接写成“缓存一定重新绑定了对象”。

## 当前设计边界

- `EiemRestoreRenderOverrides` 恢复的是登记过的 Renderer 字段，不自动覆盖游戏持有的副本或其他引用。
- `EiemRegisterAndApplyModelInstance` 在没有适用规则时直接返回。
  正常功能登记与“观察是否有残留”的职责目前耦合，空规则时缺少证据。
- 材质控制器元数据存在 `sourceMaterials` / `replacingMaterials`；其存在不能证明内容被污染。
- Mesh 资源缓存以托管 handle 非空判断命中，不等于验证 Unity 原生对象仍有效。
  本次赋值失败是否源于原生资源被卸载，尚待新日志确认。

## 需要区分的结果

1. 同一 Renderer/原生 ID 恢复后，被游戏再次写入旧生成 Mesh/材质：沿该写入入口追踪上游持有者。
2. 新 Renderer 到达时已经引用旧生成资源：定位复制/缓存来源，不把它误作新 INI 执行。
3. Renderer 字段和几何计数始终是原模型，但画面仍是 Mod：需要进一步查看实际渲染数据；
   不能仅凭 Unity getter 的成功宣称画面恢复。
4. 缓存命中 `native=0`，随后 setter 读回 null：可将赋值失败与失效原生资源建立关联。

## v40 实施：实例登记与恢复责任修正

用户授权修改 DLL 后实施，构建标记 `resource-runtime-v40-lifecycle-restore`。
这里记录已实施内容，不改写前面的 v38/v39 历史结论。

- `EiemRegisterAndApplyModelInstance` 先登记生命周期入口给出的模型，再求当前规则。
  整份 INI 为空或当前不匹配，不再阻断登记；同一 owner 换到不匹配模型也会清理旧关联。
- 已观察模型使用 `EiemUnityRef` 弱句柄；表的副本共享同一个句柄，不复制保活模型。
  弱目标过期/原生失效在刷新时清理；原生状态未知只报告并跳过，不作为有效目标或销毁证据。
  托管地址被重用时不继承旧 owner。原生存活检查来自 Unity 元数据，不硬编码对象偏移。
- 受控 Renderer 有弱引用，Mesh 修改前为原 Mesh 保留托管快照引用；
  强 GC 引用仍不保证原生资源存活，恢复前另行检查。未改用 `DontDestroyOnLoad` 等保活回退。
- 只有资源已构建、即将进入 Mesh setter 时标记写入责任；即使 setter 失败并清空字段，也保留恢复责任。
  `skip` 不再调用清空 replacement 记录的辅助函数，避免干扰独立的 Mesh 身份记账。
- 恢复期间标记 `restorePending`，原有 setter/材质提交不再重应用此记录的旧规则。
  读回失败保留原基线及待恢复状态，拒绝同对象新修改覆盖基线；恢复成功才释放记录。
  已失效 Renderer 不调用 getter/setter。材质槽及 enabled 的读回失败也保留记录。
  没有无限后台重试：后续显式重载/状态重应用才再次尝试。
- 本次没有修改生成资源缓存的淘汰策略，没有改写归池语义；
  缓存原生失效、材质控制器持有旧副本等仍需诊断证据，不能宣称换图残留已全部修好。
- 临时 `[DEBUG-residue-v39]` 探针仍保留以调查旧残留，**其标签不是 DLL 版本号**；
  版本以启动 `[BUILD] resource-runtime-v40-lifecycle-restore` 为准。

### 根因与排除边界

- **已确认的直接缺陷**：`EiemBuildMeshResource` 用文件时间戳、调色板键和非空
  `il2cpp_gchandle_get_target` 判断命中；`EiemFindCachedObject` 对 Material/Texture 也只检查托管目标非空。
  两处都没有判断 Unity 原生对象是否存活。强 GC 句柄留下托管包装，不等于原生资源仍有效。
  因而失效对象被返回给现有赋值流程，实际 Mesh 和材质槽被写成 null，造成消失。
- **缓存替换的相邻缺陷**：`EiemCacheObject` 仅淘汰同一资源不同时间戳的记录；
  将来补上原生有效性检查时，还必须处理同时间戳失效条目的替换，不能只追加新条目。
- 本次不是“未找到模型”：存活 Renderer 明确进入了替换；也不是本轮网格文件始终无法加载，
  因为 generation 2 已成功构建并写入。后续失败没有重新读取网格文件。
- 本次没有证明线程竞态：上述探针处于同一个 Unity 线程 `tid=44828`，规则发布序列与配置启停一致。
  这不等于证明全程序不存在其他并发问题。
- v40 的恢复责任修正确实覆盖到这次失败：`replacement=null` 不再导致丢失原 Mesh 恢复操作。
  **“能恢复原模型”不等于“资源缓存已正确管理”。**
- 原生资源究竟被哪个卸载/Destroy 调用销毁，本次探针没有记录调用栈，仍不能指定某个游戏函数为根因。
  也不能用本次缓存证据宣称旧版“禁用后网格和贴图重新回来”的所有持有者问题已经解决。
