# CPU 蒙皮随机躺地：当前唯一复盘

更新时间：2026-09-25

> 本文保留 2026-09-25 的取证脉络。其中“当前部署状态”和“收口计划”是当日记录，已被 [2026-09-26 统一装配状态](../unified-assembly-status-20260926.md) 更新；不要据此判断游戏目录现在安装了哪个 DLL。四槽字段实验、50 次 F10 结果和三端剩余故障以新状态页为准。

## 问题定义

Typhoea 的 `cloth01` 偶发保持 T pose 并躺在地面。`body` 通常直立，`cloth02` 的现象与 `cloth01` 不完全同步。问题既可能出现在冷启动，也可能在 F10 热重载后出现；因此不能把它归因于 F10 本身。

## 已确认的事实

1. **渲染端确实读取了替换 Mesh。** UnityPlayer 的 `C7B750` 路径从 `renderer + 0x298` 取得 native Mesh，再读取 native Mesh 的 `+0x1C8`。指针关联记录已排除“读到别的 Vulkan 对象”的解释。
2. **16/48/52 是消费端派生值，不是已经找到的单一写入 flag。** `C7B750` 将 `+0x1C8` 取值裁剪到 4 后组合绘制能力位；因此 16、48、52 分别是后续组合结果。我们目前没有证据证明某个函数直接把 48 写入 cloth。
3. **替换 Mesh 的原生私有状态与源 Mesh 不一致。** 早期边界快照中，源 Mesh 的 `+0x1C8` 稳定为 4；替换 Mesh 的 body/cloth01/cloth02 分别出现 `0x7F7FFFFF/0/24`，新一代对象也会出现其他值。替换 Mesh 的 `+0x110/+0x124` 还出现 0 和 -1，而源 Mesh 有稳定的有效值。
4. **公开蒙皮数据并非完全缺失。** 顶点、索引、bindposes 和扁平 `BoneWeight1` 已写入；`InternalSetBoneWeights` 只证明了公开可变权重载荷正确，不能证明游戏读取的 native 私有记录已经建立。
5. **body 与 cloth 的路径存在差异。** body 的源/替换状态更稳定，cloth 的私有字段和最终绘制能力位更容易变化。这解释了“body 一直直立、cloth 偶尔躺地”，但还没有定位到最终注册函数。
6. **两个静态候选已经排除。** `UnityPlayer+0x4A90D0` 调用时对象 vtable 不是 native Mesh；`+0x8455E0` 位于 PhysX 队列逻辑，不能凭一个 `[rdi+0x1C8]` store 认定为 Mesh 写入点。

## 仍未确认的部分

- 哪个构造后/注册/校验路径最终填充 native Mesh 的 `+0x1C8、+0x110、+0x124`。
- 这些字段是由 Mesh 构造函数、游戏自己的资源装配器，还是 Renderer 注册/验证阶段建立。
- 躺地样本与直立样本之间，哪一个生命周期事件或对象代际发生了分叉。
- 冷启动时出现的 cloth 消失、body 短暂回源材质，是否与同一套注册时序有关；这仍是独立的未解现象。

## 为什么迟迟没有修好

1. 之前把“最终看到的 16/48/52”当成了待修复的 flag，实际它们是消费端组合值；直接写值会掩盖根因。
2. 早期写入监视在构造函数之后才启动，可能错过最关键的初始化写入；没有形成完整的“构造 → 公开 setter → native 注册/校验 → Renderer 提交 → C7B750 消费”链条。
3. 多次静态 offset 扫描只有地址相似性，没有同时证明对象 vtable、调用上下文和目标 Mesh 身份，造成了假阳性。
4. clone、in-place 清空、只补 `InternalSetBoneWeights` 都没有复制游戏私有 native 记录；继续在 Mesh 内容上打补丁还有索引/顶点/GPU 元数据不一致导致撕裂或崩溃的风险。
5. 反复让用户长时间按 F10 只能增加样本，不能替代一次有边界的调用链取证，也造成了低帧率、卡死和日志噪声。

## 当前代码/部署状态

- 当前部署的是**只读 native Mesh 注册/校验诊断版**，不是生产修复版。
- 当前版本 Hook UnityPlayer `+0x19CE90`，在原函数前后记录目标 Renderer 的 Mesh 指针、`+0x1C8`、`+0x110/+0x124` 和 nativeData 关联，然后原样调用原函数。
- 当前诊断 DLL：`analysis/native-skin-validation-trace-20260925/eiem-native-skin-validation-trace.dll`。
- 上一版构造追踪备份：`analysis/native-skin-validation-trace-20260925/eiem-before-validation-20260926.dll`。
- 尚未宣称修复；不会修改生产 Mesh 数据，也不会硬编码 16/48/52。

### 2026-09-26 构造追踪结果

本轮日志共记录 256 次 native Mesh 构造，全部使用 Mesh vtable `0x19C8230`。每一条记录的构造前后 `+0x1C8` 完全相同，变化数为 0；因此构造函数不是当前 `+0x1C8` 写入者。返回地址主要落在 UnityPlayer RVA `0x1335E4`（129 次）、`0x464798`（124 次）和 `0x30CF23`（3 次），后续应从这些调用者进入构造后的注册/校验路径。

这也解释了为什么之前“构造后再监视写入”没有结果：真正需要追的是构造返回之后，游戏把 Mesh 纳入 Renderer/蒙皮记录的阶段。

### 2026-09-26 注册/校验追踪结果

本轮使用只读 `UnityPlayer!0x19CE90` 追踪 DLL，结果为“冷启动直立、一次 F10 后直立”，随后正常退出。

- `validationStatus=0`，钩子成功安装。
- 共记录 33 条目标 Mesh 校验记录：启动阶段 `transaction=-1` 为 32 条，F10 事务为 1 条。
- F10 事务的原函数前后完全相同：Mesh 指针、`+0x1C8`、`+0x110`、`+0x124`、底层 `nativeData` 和骨骼计数均未变化。
- 因此 `0x19CE90` 不是本轮状态变化的直接写入者；这只排除了该调用边界，不能代表躺地事务中没有其他写入。

IDA 静态结果列出了带有 `+0x1C8` 写指令的候选函数 `0x1B5430`、`0x1B56D0`、`0x1B62B0`、`0x1C43A0`。这些函数的目标对象类型尚未由运行时证据确认，不能直接当作 Mesh 写入点。下一轮改用硬件数据断点，只监视 EIEM 已发布的替换 Mesh 的 `native+0x1C8`，记录实际写入 RIP 和调用链。

## 收口计划

1. **先完成一次短构造追踪。** 只记录冷启动与一次 F10，不要求连续刷新，不按 F12；如果构造前后字段变化，沿日志栈回到写入函数。
2. **若构造函数不写这些字段，追踪低频注册边界。** 使用已校正的 Mesh `+0x110/+0x124` 标签，绑定 body/cloth01/cloth02 的 native 指针，比较直立与躺地两种代际。
3. **只在写入者和边界被证实后修复。** 优先让替换 Mesh 在游戏自己的创建/注册路径中建立完整 native 记录；PFB 只是可选入口，不要求重写 UI PFB。禁止按角色名或固定 flag 值补丁。
4. **修复后才做稳定性验收。** 冷启动多轮、手动 100 次 F10，检查 body/cloth01/cloth02 姿态、cloth 消失/回源材质、GPU 撕裂和崩溃。测试期间日志限时、限条数，绝不自动连按 100 次。

## 一句话结论

根因已经收窄为“替换 Mesh 进入游戏原生渲染注册链时，私有 native 蒙皮元数据没有按源 Mesh 的方式建立或被后续校验重置”；但**具体写入者尚未证实**，所以现在不能说已经修好，也不能用一个固定 flag 值收尾。
