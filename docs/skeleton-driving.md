# 共享骨架驱动：源节点引用与新增骨骼

现行 Skeleton v1/v2 契约；新增节点装配初次实现于 DLL v48 / Blender 0.10.0。
当前插件版本与工作区状态见[文档索引](README.md)。

状态：已实现读写、实例内创建与 Mesh 骨骼绑定；**游戏自定义 GPU 蒙皮尚未验收**。
本轮不实现物理链、碰撞体、Avatar 替换或新增动画曲线，不修改用户工程和游戏 Mod。

## 1. 这轮补齐什么

- `Skeleton` 不再只是 INI 中能解析的声明。`Render.skeleton` 现在由运行时装配器消费。
- 沿用角色已有共享骨架；源节点只按路径引用，不复制每个部位的骨架，不写源节点的 TRS。
- 新骨骼在该模型实例的对应父节点下创建，写入作者局部位置、旋转、缩放。
  它随父节点变换运动；这不等于自动拥有独立动画曲线或物理模拟。
- Mesh 的局部骨骼表逐项映射到这份实例骨架。原槽（包括零权重槽）及原 bind pose 不变，
  新槽追加，新增骨骼的绑定矩阵由作者姿态和已知源绑定空间计算。
- 同一 Mod 的同一 Skeleton 资源、同一模型实例共用一组新增节点；不同实例不共享 Transform。
  不同 Mod 的新增节点也分开，不靠角色名或 PFB 名称硬编码。

对应实现：[资源文档](../src/eiem_skeleton_document.h)、[Unity 装配器](../src/eiem_skeleton_runtime.h)、
[Render 执行与恢复](../src/il2cpp_trace.h)、[Blender 读写](../tools/Blender/eiem_blender_addon.py)。

## 2. 作者操作

1. 导入离线完整 EIEM 包，保留原共享 Armature。
2. 在该 Armature 的编辑模式中新增骨骼，设置父级和绑定姿态。
   首轮用 `Shift+A` 创建干净骨骼；不要直接复制带源身份自定义属性的旧骨骼。
   若复制出了重复源路径，导出器会报错，不会猜测哪根骨骼是真的源节点。
3. 网格 Armature 修改器仍指向这个共享骨架；用新增骨骼名称建立顶点组并赋权重。
4. 导出时显式选择要处理的网格和这一个共享 Armature，导出到新的 Mod 文件夹。
   有新增骨骼却未选骨架会报错；只有沿用源骨骼时，不必导出 Skeleton。
5. 骨架文件和 `skeleton=...` 由导出器生成，不要求用户填写骨骼序号或手写 INI。

源骨骼的改父级、改绑定姿态暂不支持，导出时明确拒绝，不悄悄输出旧值。
对新骨骼，导出实际编辑姿态，不使用单位旋转占位。父节点的原生缩放参与换算；
不能表达为局部 TRS 的剪切明确拒绝。显示名修改与源完整路径分开。

相机开关语义不变：选中且相机关生成 `handling=skip`；未选独立源资源不生成动作。
骨骼修改不改变材质、切线、UV 或形态键的现有契约。

## 3. INI 与二进制契约

```ini
[SkeletonCharacter]
path=skeletons/character.skeleton

[MeshCloth]
path=meshes/cloth.mesh

[RenderCloth]
asset=SourceCloth
mesh=MeshCloth
skeleton=SkeletonCharacter
```

仍由 Render 命中消费者并装配资源。Skeleton 不负责命中，不独立替换 Animator。
`partner.N` 引用的 Render 模板也可以指定同一个 Skeleton；它必须显式声明该依赖。
仅写 `skeleton` 可建立节点，但不会擅自改变源 Mesh 的骨骼索引或赋权重。

`.skeleton` 为小端；字符串沿用既有 7-bit 长度 + UTF-8：

| 顺序 | 内容 |
|---|---|
| 头 | 8 字节 `EIESKEL\0`、int32 版本、坐标标记 `unity-y-up-left-handed` |
| 层级 | int32 节点数；每项为路径、int32 父索引、float3 局部位置、float4 四元数 xyzw、float3 局部缩放 |
| 既有尾字段 | int32 0、int32 -1；Mesh 的局部骨骼表不放在 Skeleton 中 |
| v2 来源尾表 | int32 节点数，随后每节点 1 字节：1=引用源节点，0=新增节点 |

节点父级必须先出现，路径唯一且与父子结构一致；允许 AnimeStudio 的空字符串资源根路径。
文件限 16,384 节点、单路径 4,096 UTF-8 字节；非有限数、无效旋转、非正缩放、截断或尾随数据拒绝。
新增节点不能作为源节点的父级。

AnimeStudio 当前源包为 v1，DLL 将其全部视为源引用；Blender 导出 v2，明确保留来源。
这是同一个 Skeleton 文档模型的来源信息扩展，不是两套驱动算法。
缺失源节点绝不自动转成新增节点。骨架资源段名冲突在导出时消歧，Render 按实际 Armature 关联；
不能因两个作者骨架段名相同而覆盖文件或串绑。

## 4. 运行与生命周期

1. 在 Unity 线程，从命中 Renderer 的骨骼祖先路径锚定当前模型根；支持空资源根。
2. 验证该根下所有源节点引用。只遍历该实例，不扫描其他角色借骨骼。
3. 创建新增 Transform，先父后子。运行时使用 Mod 私有名称；Mesh 路径通过明确的节点表解析，
   不把私有名称当作源路径，也不把源节点缺失掩盖成创建成功。
4. 构造与 Mesh 局部表顺序一致的 `Transform[]`；接入现有 Mesh 赋值、bones 赋值及游戏刷新路径。
   数组持有托管引用；原恢复基线与替换数组分开。
5. Render 状态持有骨架引用。F10/条件切换先恢复源 Mesh 和 bones，确认成功再释放引用。
   恢复失败保留基线及新增节点，并报告；不能先删除骨骼再重试恢复。
6. Partner 的原生 Destroy 是延迟的。即使 C++ 状态已经移除，骨架仍保留其弱引用，
   直到确认原生消费者已销毁才允许释放节点。未知存活状态不是销毁证据。
   源 Renderer 的 owner 卸载回调同理：丢掉装配记录不代表原生 Renderer 已销毁，
   未经恢复的消费者会保留到原生销毁；若对象仍在池中，就不提前销毁它可能引用的骨骼。
7. 无消费者的节点按子到父顺序分离、销毁，绝不销毁源节点。创建失败的半成品也纳入同一清理路径。
   释放失败保留记录，后续 reconcile 再处理；这不是换另一条绑定算法兜底。
8. 正在退役的旧代不复用；新代可创建私有节点，等待原生销毁的旧代由后续 reconcile 回收。
   未恢复仍在使用的同一资源文件若变化则拒绝直接串换，要求经过重载流程。

若多个冲突规则试图在同一未恢复 Renderer 上挂不同骨架，拒绝后来的绑定，
避免把旧 Mesh 仍引用的节点释放。沿用当前规则优先级，不新增隐式合并策略。

## 5. 验证与尚待确认项

自动验证分三部分，不把它们称为游戏画面验证：

- 实际 C++ reader + Unity 适配器测试：v1/v2、空根/命名根、缺失源节点、无效文件、
  新节点局部 TRS、两个部位共享、两个角色实例隔离、不同 Mod 同名骨骼、原节点零写入、
  文件变化、失败构建清理、退役对象不复用、非 Unity 线程不释放、延迟 Partner 销毁。
- 实际 Blender 5.0.1：新增父子骨骼、带旋转和缩放的源父级、局部矩阵与显示姿态一致、
  原零权重槽/绑定矩阵保持、Mesh 骨骼索引正确、两个 Mesh 共用一个 Skeleton、
  缺失骨架依赖拒绝、保存重开工程后字节一致、源姿态修改不破坏既有导出。
- 实际恢复函数回归：失败保留骨架引用；源 Mesh/bones 恢复或原生 Renderer 销毁后才释放。
  owner 卸载但原生消费者尚存时记录待释放引用；非 Unity 线程只登记引用，不调用原生对象方法。

游戏中仍须验证：新增槽是否被自定义蒙皮管线读取、父骨骼动作是否正确影响新增骨骼、
大世界/角色 UI/换图/开启关闭/F10 是否一致。`[SKELETON] Ready` 只证明节点表建立，
不是 GPU 提交或画面正确的证据。当前没有盲调 `Animator.Rebind`、`CreateClothBindings`、
`BuildAndRun`，也没有猜写 GPU 缓冲偏移。

物理写回、额外动画驱动、Avatar/IK 完整重绑定仍见 [物理设计](physics-authoring-design.md)，另行实现和验收。
